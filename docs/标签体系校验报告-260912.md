## 二、链路结构

```
             ┌──────────────────────┐
  前台筛选页 │ personal-care/product-finder   → Tag.list({productLine:'pc'})
             │ personal-care/formulation-finder → Tag.list({productLine:'formulation'})
             │ pharmaceuticals/product-finder   → Tag.list({productLine:'pharma'})
             └──────────────┬───────┘
                            │  GET /api/tags?productLine=xxx  （公开，无需登录）
                            ▼
             ┌──────────────────────┐
    字典      │  tag_dictionary      │  255 条
             │  pc 51 / formulation 112 / pharma 48 / article_theme 44
             └──────────────┬───────┘
                            │  只返回 {label, value}
                            ▼
             ┌──────────────────────┐
  后台管理页  │ admin/tag-manage-standalone.html（iframe 嵌入 /admin）
             │   ↑ 这里读的是同一个 /api/tags，所以缺 id / sortOrder
             └──────────────────────┘
                            │
                            ▼
             ┌──────────────────────┐
  产品字段    │ pc_ingredients(57)  功能/应用/概念/声明/特征/自然性
             │ formulations(99)    应用/性状/声明/成分/天然指数
             │ pharma_products(54) 市场/给药途径/功能/剂型
             │ 标签以「逗号分隔字符串」存放
             └──────────────────────┘
```

关键点：**前台与后台读的是同一个接口 `/api/tags`（分组、只有 label+value）**，而产品字段里存的是**选项值**（`value`）。
所以「对齐」的判定标准就是：`产品字段里的每一项` 是否都能在 `同产品线同分类的字典 value` 里找到。

### 为什么会这样

`backend/scripts/sync-tag-dictionary.ts` 曾把 **pc** 字典从原中文站 API 全量重灌（`label=value=中文名`），
所以 pc 六个维度只有 `claim` 漏了。**配方与药用辅料从未跑过同等处理**，字典还是早期人工种的老词表，
产品数据却是从中文站导入的——两套词表各说各话。

### 典型的「差一个字」错配

同一个概念，字典和数据用了不同译法，于是既产生缺口、又产生死标签：

| pharma/functionality | 生物利用度增强剂 | 口服生物利用度增强剂 | 17 |
| pharma/functionality | 润滑剂 | 片剂润滑剂 | 4 |
| pharma/dosage_form | 乳膏 | 乳膏剂 | 19 |
| pharma/dosage_form | 软膏 | 软膏剂 | 14 |
| pharma/dosage_form | 凝胶 | 凝胶剂 | 3 |
| pharma/dosage_form | 颗粒 | 颗粒剂 | 5 |
| formulation/claim | 光老化 | 抗光老化 | 11 |

### 最大的两个洞

* **配方 `form`：34% 的产品筛不出来** —— `乳剂/啫哩` 被 34 个配方使用，字典里却没有它
* **配方 `ingredient`：53 条死标签** —— 字典里是去掉了 `®`/`™` 的名字（`Emulium Kappa MB`），
  数据里带符号（`Emulium® Kappa MB`），两边对不上；同时 17 个真实成分不在字典里

### 值得注意的脏数据（应为导入时未清洗）

* `formulations.claim_tag` 中出现 `+`、`含有`、`面部`、`身体`、`眼部`、`AHA&nbsp;` —— 明显是页面标签被误当成分声明抓进来了
* `formulations.claim_tag` 里 `#103` 一条记录的 `+` 出现了两次（重复值）
* `pc_ingredients.claim_tag` 里有 `活性质地&mdash;保湿` —— HTML 实体未解码（`&mdash;`）
* 字典 `article_theme/theme` 中 `质地` 出现两次（`texture` 与 `textures` 同译），属重复 value
* 字典 `pc/claim` 中 `充满活力_` 结尾带下划线 —— 疑似脏数据
* `TagDictionary` 表**没有任何唯一约束**，重复条目可以无限插入

## 五、筛查功能（4 类缺陷，均已线上实测）

### 1. 同分类多选：PC 与药用辅料是「交集」，不是「并集」

`pc-ingredient.controller.ts` L54-68 与 `pharma.controller.ts` L47-62：
把每个选中值各生成一个 `{field: {contains: v}}`，再整体塞进 `where.AND`。
→ 同分类选两个值，要求产品**同时**拥有两者。

```
PC  functionality=活性物          → 23 个
PC  functionality=润肤剂          →  4 个
PC  functionality=活性物,润肤剂   →  0 个   ❌ 期望并集 27 个
```

### 2. 配方筛选：只认第一个值

`formulation.controller.ts` L50：`where[field] = { contains: vals[0] }` —— 其余选中项被静默丢弃。

```
formulations claim=保湿       → 32 个
formulations claim=清爽       → 21 个
formulations claim=保湿,清爽  → 32 个   ❌ 期望并集 49 个（第二个值被丢掉）
```

### 3. `contains` 子串匹配 → 误命中

三个控制器统一用 `contains`，而标签是**逗号分隔字符串**，于是子串会互相命中。
极端情况：**字典里的"死标签"点了照样出结果**——

```
"乳化剂"  （字典有，0 个产品使用）→ 命中 9 个（实为「外用乳化剂」）
"软膏"    （字典有，0 个产品使用）→ 命中 14 个（实为「软膏剂」）
"凝胶"    （字典有，0 个产品使用）→ 命中 4 个（实为「凝胶剂」「双凝胶」）
"缓释"    （字典有，0 个产品使用）→ 命中 3 个（实为「缓释制剂」）
"润滑剂"  （字典有，0 个产品使用）→ 命中 4 个（实为「片剂润滑剂」）
```

这会让用户困惑：**筛选器里一个"没人用的标签"，却筛出了产品**；反过来也会漏掉（选「软膏剂」时若数据里是「软膏」则查不到，视方向而定）。

### 4. 数据里的标签，前端根本不显示选项

字典里没有的值，前台筛选器不会渲染成可点选项 —— 这些产品的这个维度**无法被筛出**：

```
pharma/dosage_form  「乳膏剂」：字典没有 → 涉 19 个产品（接口手输参数能查到，但界面上没有入口）
formulation/form    「乳剂/啫哩」：字典没有 → 涉 34 个产品（占 34%）
```

## 六、新标签自动补齐：**目前不具备**

排查了所有会写字典的代码路径：

| 路径 | 是否自动补齐 | 说明 |
|---|---|---|
| 后台新增标签 `POST /api/tags` | ❌ | 纯手工录入，且**无去重、无唯一约束** |
| 产品导入 `import.controller.ts` / `import-rules.ts` / `import-verify.ts` | ❌ | **完全未引用** `tag_dictionary`，导入的标签不会入库 |
| `utils/article-theme.ts` → `ensureArticleThemeSeed()` | ⚠️ 部分 | **唯一一处自动补齐**，但只覆盖"文章主题"标签：把代码里的静态表 `TAG_ZH` 幂等灌进字典。它也不是"扫描发现新标签"，未命中的词会被记入 `unknownSink` 待人工处理 |
| `scripts/sync-tag-dictionary.ts` | ⚠️ 手动 | 从原中文站 API 全量重灌字典，**只支持 pc**，需人为执行 |
| `scripts/fix-formulation-tags.ts` | ⚠️ 手动 | 一次性修配方 application/form，含硬编码映射表 |

结论：**产品侧的标签没有任何自动补齐**。
一旦导入一个带新标签的产品（或前端页面引用了字典外的标签），就会出现：
字典不显示 → 后台管不到 → 前台筛不出 → 且**没有任何提示或告警**。

## 七、修复清单（建议按此顺序）

### P0 — 后台不可用，必须先修

1. `tag-manage-standalone.html`：`formula` → `formulation`（4 处 `<option>`）
2. `tag-manage-standalone.html`：`CATEGORY_MAP.pharma` 改为 `['market','route','functionality','dosage_form']`；
   `CATEGORY_LABELS` 补齐 `market`（应用市场）/ `route`（给药途径）/ `dosage_form`（剂型），删掉 `dosageForm`
3. `tag-manage-standalone.html`：`CATEGORY_MAP.pc` 删掉 `'label'`
4. **编辑 / 删除按钮**：`getTagDictionary()` 返回值补上 `id`、`category`、`sortOrder`
   （当前表格渲染 `${t.sortOrder || 0}` 恒为 0，`editTag` 拿 `t.value` 当 id → `parseInt('活性物') = NaN` → 后端必抛错）

### P1 — 数据与筛查

5. 统一多选语义：**同分类 OR、跨分类 AND**（PC / 药用辅料改 `OR`，配方去掉 `vals[0]`）
6. `contains` 换成分隔符精确匹配（逗号分隔字段可用 `OR: [{f:v},{f:{startsWith:v+','}},{f:{endsWith:','+v}},{f:{contains:','+v+','}}]`）
7. 字典对齐：把 `sync-tag-dictionary.ts` 扩展为**覆盖三条产品线**，或新写一个「从产品数据反向聚集」的脚本
   —— 这一步同时消灭 117 条缺口与 116 条死标签
8. 清洗脏数据：`+` / `含有` / `面部` / `AHA&nbsp;` / `活性质地&mdash;保湿` / `充满活力_` / 重复的「质地」

### P2 — 机制

9. `TagDictionary` 加 `@@unique([productLine, category, value])`，`createTag` 前置去重
10. 新增「标签健康检查」：导入完成后自动比对新标签，后台给出一键补齐的 diff 预览（预留人工确认，不静默写入）
11. 前台筛选器：字典接口返回分组时，可按需附带"命中产品数"，为 0 的维度置灰，避免用户点空列表
