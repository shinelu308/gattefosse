## 二、链路结构

```
             ┌──────────────────────┐
  前台筛选页 │ personal-care/product-finder   → Tag.list({productLine:'pc'})
             │ personal-care/formulation-finder → Tag.list({productLine:'formulation'})
             │ pharmaceuticals/product-finder   → Tag.list({productLine:'pharma'})
             └──────────────┬───────┘
                            │  GET /api/tags?productLine=xxx  （公开，无需登录）
                            ▼
             ┌──────────────────────┐
    字典      │  tag_dictionary      │  255 条
             │  pc 51 / formulation 112 / pharma 48 / article_theme 44
             └──────────────┬───────┘
                            │  只返回 {label, value}
                            ▼
             ┌──────────────────────┐
  后台管理页  │ admin/tag-manage-standalone.html（iframe 嵌入 /admin）
             │   ↑ 这里读的是同一个 /api/tags，所以缺 id / sortOrder
             └──────────────────────┘
                            │
                            ▼
             ┌──────────────────────┐
  产品字段    │ pc_ingredients(57)  功能/应用/概念/声明/特征/自然性
             │ formulations(99)    应用/性状/声明/成分/天然指数
             │ pharma_products(54) 市场/给药途径/功能/剂型
             │ 标签以「逗号分隔字符串」存放
             └──────────────────────┘
```

关键点：**前台与后台读的是同一个接口 `/api/tags`（分组、只有 label+value）**，而产品字段里存的是**选项值**（`value`）。
所以「对齐」的判定标准就是：`产品字段里的每一项` 是否都能在 `同产品线同分类的字典 value` 里找到。

## 五、筛查功能（4 类缺陷，均已线上实测）

### 1. 同分类多选：PC 与药用辅料是「交集」，不是「并集」

`pc-ingredient.controller.ts` L54-68 与 `pharma.controller.ts` L47-62：
把每个选中值各生成一个 `{field: {contains: v}}`，再整体塞进 `where.AND`。
→ 同分类选两个值，要求产品**同时**拥有两者。

```
PC  functionality=活性物          → 23 个
PC  functionality=润肤剂          →  4 个
PC  functionality=活性物,润肤剂   →  0 个   ❌ 期望并集 27 个
```

### 2. 配方筛选：只认第一个值

`formulation.controller.ts` L50：`where[field] = { contains: vals[0] }` —— 其余选中项被静默丢弃。

```
formulations claim=保湿       → 32 个
formulations claim=清爽       → 21 个
formulations claim=保湿,清爽  → 32 个   ❌ 期望并集 49 个（第二个值被丢掉）
```

### 3. `contains` 子串匹配 → 误命中

三个控制器统一用 `contains`，而标签是**逗号分隔字符串**，于是子串会互相命中。
极端情况：**字典里的"死标签"点了照样出结果**——

```
"乳化剂"  （字典有，0 个产品使用）→ 命中 9 个（实为「外用乳化剂」）
"软膏"    （字典有，0 个产品使用）→ 命中 14 个（实为「软膏剂」）
"凝胶"    （字典有，0 个产品使用）→ 命中 4 个（实为「凝胶剂」「双凝胶」）
"缓释"    （字典有，0 个产品使用）→ 命中 3 个（实为「缓释制剂」）
"润滑剂"  （字典有，0 个产品使用）→ 命中 4 个（实为「片剂润滑剂」）
```

这会让用户困惑：**筛选器里一个"没人用的标签"，却筛出了产品**；反过来也会漏掉（选「软膏剂」时若数据里是「软膏」则查不到，视方向而定）。

### 4. 数据里的标签，前端根本不显示选项

字典里没有的值，前台筛选器不会渲染成可点选项 —— 这些产品的这个维度**无法被筛出**：

```
pharma/dosage_form  「乳膏剂」：字典没有 → 涉 19 个产品（接口手输参数能查到，但界面上没有入口）
formulation/form    「乳剂/啫哩」：字典没有 → 涉 34 个产品（占 34%）
```

## 六、新标签自动补齐：**目前不具备**

排查了所有会写字典的代码路径：

| 路径 | 是否自动补齐 | 说明 |
|---|---|---|
| 后台新增标签 `POST /api/tags` | ❌ | 纯手工录入，且**无去重、无唯一约束** |
| 产品导入 `import.controller.ts` / `import-rules.ts` / `import-verify.ts` | ❌ | **完全未引用** `tag_dictionary`，导入的标签不会入库 |
| `utils/article-theme.ts` → `ensureArticleThemeSeed()` | ⚠️ 部分 | **唯一一处自动补齐**，但只覆盖"文章主题"标签：把代码里的静态表 `TAG_ZH` 幂等灌进字典。它也不是"扫描发现新标签"，未命中的词会被记入 `unknownSink` 待人工处理 |
| `scripts/sync-tag-dictionary.ts` | ⚠️ 手动 | 从原中文站 API 全量重灌字典，**只支持 pc**，需人为执行 |
| `scripts/fix-formulation-tags.ts` | ⚠️ 手动 | 一次性修配方 application/form，含硬编码映射表 |

结论：**产品侧的标签没有任何自动补齐**。
一旦导入一个带新标签的产品（或前端页面引用了字典外的标签），就会出现：
字典不显示 → 后台管不到 → 前台筛不出 → 且**没有任何提示或告警**。

> 已于 P2 补上**发现与提示**机制（但**不改变「不自动入库」这个设计**）：产品保存时响应附 `tagWarnings`；
> 后台「一致性检查」面板给出缺口 diff 预览 + 一键补齐（需人工确认）；CLI `check-tag-health.js --strict` 可作导入收尾闸门。见第九节。

**9. 唯一约束 + `createTag` 前置去重**

⚠️ 审计报告最初建议的 `@@unique([productLine, category, value])` **是错的**，会误杀文章主题：
`texture` 与 `textures` 都译作「质地」是**合法的同译**（实测 id 524/525），实测 `label !== value` 的 44 条**全部**在 `article_theme`。
真正落地的约束是两条：

| 索引 | 定义 | 覆盖 |
|---|---|---|
| `uq_tag_dict_label` | `UNIQUE(product_line, category, label)` | 四条线通吃 |
| `uq_tag_dict_value` | `UNIQUE(product_line, category, value) WHERE product_line <> 'article_theme'`（**部分索引**） | 三条产品线 |

Prisma schema 无法表达部分索引，所以 `value` 那条只能用 raw SQL 建（脚本 `backend/scripts/add-tag-dict-indexes.js`，支持 dry-run / `--apply`）。
`createTag` 命中重复时返回 **200 + `success()`** 而不是 409 —— 前端 axios 对非 2xx 直接 reject，拿不到 message，用户只会看到 `Request failed with status code 409`。

**10. 标签健康检查（diff 预览 + 人工确认，不静默写入）**

新增 `backend/src/utils/tag-health.ts`，四类问题一起扫：

| 类别 | 判定 |
|---|---|
| 缺口 | 产品数据里有、字典里没有（附命中产品数 + 样本） |
| 死标签 | 字典里有、没有任何产品在用（前台会点出空列表） |
| 同值冲突 | 同分类同 value 多条 |
| 结构性脏值 | 只认结构性垃圾：HTML 实体残留 / 首尾是 `+ , 、` 等分隔符 / 纯符号 / **括号不成对** |

> ⚠️ 脏值判定**刻意不做**长度规则与「含『的』」规则：字典里就有 `有趣的质感`、`NOI = 100 % (ISO 16128)`、`符合中国标准 (IECIC)`、`口服生物利用度增强剂`，任何长度规则都会误报；
> 括号只能用**深度扫描配对**判断，`乳化剂(O/W)`、`硬脂（栓剂基质）` 都是配对合法的正常标签（首版与二版正则共误报 24 条，已修）。

接口：`GET /api/tags/health`（扫描）· `POST /api/tags/health/fill`（按需补齐，body 传 `{line, items:[{category,label,value}]}`）· `GET /api/tags/lines`（分类元数据）。
后台 `tag-manage-standalone.html` 新增「一致性检查」面板：勾选要补的缺口 → **弹确认框** → 补齐 → 自动重检。
产品保存时响应会附带 `tagWarnings`，编辑完立刻知道「刚写进去的标签字典里还没有」。

**11. 前台 0 命中置灰**

字典接口支持 `?withCount=1`，条目附 `count`（命中产品数）。三个筛选页把 `count === 0` 的项加 `is-empty`：`opacity:.4` + `pointer-events:none`（一次拦掉 checkbox / 链接 / 更多信息，不必改各处 handler）。
`facet-item` 的 class 统一由 `facetClass(c)` 生成，避免「重置选中态时把 `is-empty` 丢掉」。

## 九、机制与日常运维

### 1. 单一真相源：`backend/src/utils/tag-map.ts`

映射（产品线 → 表 / 字段 / 物理列 / 前台 query 参数 / 是否多值）过去**散落三处**（三条 controller + 后台 `CATEGORY_MAP` + 审计脚本），历史上因此踩过两次坑：
`formula` vs `formulation` 导致后台查不到配方；pharma 分类表列错导致 29 条药用辅料不可见。
现在全部集中到 `tag-map.ts`：

```ts
TAG_LINES.pc.dimensions = [
  { category:'functionality', field:'functionalityTag', column:'functionality_tag',
    param:'functionality', label:'功能', multi:true },
  // ...
]
```

**以后新增 / 改名一个标签维度，只改这一个文件。** 三条 controller 用 `buildTagFilters(line, req.query)` 自动派生，后台的分类下拉与标称来自 `GET /api/tags/lines`（= tag-map 声明 ∪ 库中实际存在的 category，所以「字典里有、后台看不到」不可能再发生）。

> ⚠️ 两处「看着像笔误、其实不能改」：
> `formulation.ingredient` 维度的 field 是 `conceptTag`、param 是 `ingredient`；`formulation.naturalityIndex` 是 `multi:false`（存的是 `> 95%` 这类整串，不能按逗号切）。

### 2. 导入产品后的收尾（很重要）

产品导入链路**仍然不写字典**（审计第六节结论不变）。所以导入完请跑一次：

```bash
cd backend && npx tsc                                   # 先编译，CLI 依赖 dist/utils/tag-health.js
node scripts/check-tag-health.js                        # 看三条线的缺口 / 死标签 / 脏值
node scripts/check-tag-health.js --line=pc --strict     # 只看 pc，有缺口则退出码 1（可接进导入脚本收尾）
node scripts/check-tag-health.js --line=pc --fill       # 补齐（幂等，已存在则跳过，sortOrder 取该分类最大值+1）
```

### 3. 线上必须手动做的一步

唯一索引建在 **SQLite 数据文件**里，**不随 deploy 走**（`*.db` 不部署）。所以部署后要 SSH 到线上再执行一次：

```bash
cd /opt/gattefosse/backend
node scripts/add-tag-dict-indexes.js            # dry-run：列重复组
node scripts/add-tag-dict-indexes.js --apply    # 建索引（IF NOT EXISTS，可重复执行）
```
