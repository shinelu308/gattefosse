# 页面区块化方案（参照产品的 content_blocks）

日期：2026-09-12
问题：内容管理里的独立页面，能不能像文章板块那样实现「后台可编辑、前台自动渲染」？

---

## 一、结论先说

**能，而且比预期近得多。**

后台的「页面区块编辑器」**已经建好了**——`内容管理 → 站点内容管理 → 编辑页面` 有三个 tab（基本信息 / 区块内容 / HTML 源码），区块内容 tab 里已经有 **10 种区块类型**、上移下移、删除、以及「搜索产品自动填充」的联动。

后端接口也齐了。**唯一缺的是前端：把 `content` 里的区块数组渲染出来。**

## 三、方案（三档）

### 档 1｜只接通头部 hero —— 低风险，立刻见效

**做什么**：把 23 个页面写死的 hero 改成读后台 hero 区块。

**改哪**：每个 `site/<page>.html` 的 hero 段（约 8-15 行）

**怎么改**：静态内联背景**保留作兜底**，Vue `:style` 叠加覆盖——

```html
<div class="s-banner__item"
     style="background-image:url('旧图')"
     :style="{ backgroundImage: hero.backgroundImage ? `url('${hero.backgroundImage}')` : '' }">
  <h1>{{ hero.title || '静态兜底标题' }}</h1>
  <p>{{ hero.summary || '静态兜底摘要' }}</p>
</div>
```

> ⚠️ **必须保留静态内联兜底**。这是 260912 刚修过的时序竞态教训：首屏资源若只靠「元素就位后由 JS 设上去」，慢加载下会静默失效成灰块。静态 style 打底 + Vue 覆盖，是唯一稳的写法。

- 后端 0 改动、后台 0 改动
- **收益**：26/31 页的头部（标题 / 摘要 / 背景图 / 按钮 / 视频）可在后台改
- **不解决**：正文仍是 HTML blob

---

### 档 2｜正文区块化 —— 主方向，分两步走

#### 2a｜前端通用区块渲染器（不动数据，随时可回退）

**新建** `site/js/page-blocks-260912.js`，导出一个 Vue 组件 `<page-blocks>`：

- props：`blocks`（数组）/ `fallbackHtml`（字符串）
- **渲染规则**：`blocks` 非空 → 逐块按 `type` 分发渲染；`blocks` 为空 → 回落 `v-html="fallbackHtml"`
- 10 种类型各一段模板，**字段名直接对齐后台已有表单**，per-type 写法照抄产品详情页（`site/personal-care/product-finder/product-detail.html` 503-645 行已验证）

**每个页面只改 2 处**：

```js
// 数据层：解析出 blocks
blocks: (() => { try { return JSON.parse(p.content || '[]'); } catch (e) { return []; } })()
```

```html
<!-- 渲染层：一行替换 -->
<page-blocks :blocks="data.formData.blocks" :fallback-html="data.formData.content"></page-blocks>
```

> 这一步是**纯叠加**——`blocks` 为空时行为与现状**完全一致**。所以 28 个页面可以逐页灰度切、出问题单独回退，不存在「一刀切坏全站」的风险。

#### 2b｜把现有正文切块入库 —— 三种做法，请挑一种

26 页的正文现在是一整块 HTML（原站 Drupal 面板拼出来的 `.node__content` + 聚合 div），**没有稳定的块边界，自动切块一定会切歪**。所以不建议无脑自动切：

| | 做法 | 质量 | 成本 |
|---|---|---|---|
| **(i)** | **人工重建**：挑重点页（about-us / expertise / CSR 三页 / 各技术页）在后台用区块重搭 | 最高 | 高，按页算 |
| **(ii)** | **半自动**：脚本按 `h2` 切段生成 `text` 草稿，启发式识别「图+文」生成 `imagetext`，产出候选块让人工在后台确认 | 中 | 中 |
| **(iii)** | **保持 HTML**：老页面继续走 fallback，只有新页面 / 改造过的页面用区块 | — | 最低，但长期两套并存 |

---

### 档 3｜列表区块化 —— 建议不做

新增 `blockType: news_list / product_list`，`content` 存 `{ source, category, limit }`。

列表数据已经有专门的管理页（新闻 / 文章 / 研讨会 / 出版物 / 杂志），再包一层区块收益很低。**先不做。**

## 四、架构决策：要不要给页面也建独立表？

| | 做法 | 好处 | 代价 |
|---|---|---|---|
| **A（推荐）** | 沿用 `page_contents.content` JSON 列 | 后台编辑器 / 后端接口 / 已接 3 页 **100% 复用，0 改动** | 不支持单块 `isPublished`；整页一次性保存（多人同时编辑会互相覆盖） |
| B | 新建 `page_blocks` 表（照 `content_blocks`） | 单块增删改、单块下线、编辑粒度细 | 后台 10 种类型的表单是围绕 `_blocks` 数组写的，要重写；后端新增 5 个接口；前端换数据源；26 页存量 JSON 要迁移 |

**推荐 A。** 页面编辑的粒度本来就是「整页一次保存」，不像产品那样需要单独下线某个技术文件。B 的代价几乎全花在「把一个已经能用的东西拆开重装」。

---

## 五、上线前必须先修的一个坑

`content` 与 `content_html` 现在**同时存在且语义重叠**，必须先定死优先级，否则会出现「后台以为清空了、前台还在显示老 HTML」。

**建议规则**：`content` 数组非空 → 用区块；为空 → 用 `content_html`。

同时后台那句提示文案与实际行为不一致，要一起改：

- 文案（`admin/index.html` 4230 行）说：「保存时将以『HTML 源码』内容为主，区块内容将被清空」
- 实际代码（8437-8443 行）：只有 `_blocks.length === 0` 时才把 `content` 置 null；`contentHtml` 是独立字段，`savePageContent` 里 `contentHtml: contentHtml || null`

两者对不上，得对齐。

## 六、推荐路线

1. **档 1**（接通 hero）——半天见效，覆盖 26 页，零架构风险
2. **档 2a**（前端渲染器 + fallback）——打通「整页后台可编辑」，不破坏任何现有页面
3. **档 2b**——按节奏决定 (i)/(ii)/(iii)，重点页优先
4. **档 3**——先不做
